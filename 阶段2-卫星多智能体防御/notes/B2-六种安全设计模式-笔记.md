# B2 笔记：六种安全设计模式

> **论文**：Design Patterns for Securing LLM Agents against Prompt Injections
> **作者**：Luca Beurer-Kellner（Invariant Labs）、Beat Buesser（IBM）、Edoardo Debenedetti（ETH）、Florian Tramèr（ETH）、Andrew Paverd（Microsoft）等 14 人（**Google / IBM / Microsoft / ETH / EPFL 等联合，作者按字母序**）
> **出处**：arXiv:2506.08837 · 2025-06
> **本地 PDF**：`papers/B2 - Design Patterns for Securing LLM Agents (2506.08837).pdf`（32 页）
> **一句话**：给出**一套**有**可证明抗注入性**的 Agent 设计模式，逐个分析**安全性与可用性的取舍**，并用案例说明适用场景。

---

## 一、为什么要"设计模式"而不是"更好的过滤器"

论文的出发点：**提示注入的根因是 LLM 分不清指令和数据**。既然这个根因短期消不掉，那就**改架构**——让架构本身保证"即使模型被骗，也不会造成后果"。

关键词是 **"provable resistance"（可证明的抗性）**：不是"我们测了很多攻击都拦住了"，而是"**结构上攻击不可能成功**"。

---

## 二、五个模式（按"限制从松到紧"排列）

### ① Action-Selector（动作选择器）—— 最严格
**做法**：**切断工具输出回流给 Agent 的通道**。Agent 只当一个"动作选择器"，把用户请求翻译成一个允许动作的调用，**动作的结果不再回到 Agent**。
**效果**：**对提示注入免疫**。
**代价**：**几乎放弃了自主性**——没有反馈就没有多步推理。

### ② Plan-Then-Execute（先规划后执行）
**做法**：允许工具输出回流，但**输出不能影响"要执行哪些动作"**。Agent 先定死一个工具调用计划，之后按计划执行。
**效果**：注入可以改工具调用的**输入**，但改不了**动作序列**。
**代价**：计划定死，遇到需要临机应变的任务就不好用。

### ③ LLM Map-Reduce（LLM 分治）
**做法**：把任务拆成互不影响的子任务，每个子任务由独立的 LLM 实例处理，**结果由外层代码（不是 LLM）汇总**。
**效果**：一个子任务的注入传不到其他子任务。
**代价**：只适合可拆分的任务。

### ④ Dual LLM（双 LLM）
**做法**：**特权 LLM**（处理可信输入、做决策）和**隔离 LLM**（只处理不可信数据）分开。隔离 LLM 只输出**受限格式**的内容（如回答选择题、填槽位），**它的话不能直接变成动作**。
**效果**：不可信数据接触不到决策环节。
**代价**：需要设计"受限交互协议"（隔离 LLM 能用什么形式回答）。

> 这个模式就是 **B1（CaMeL）的理论基础**——Willison 2023 提出，CaMeL 把它工程化了。

### ⑤ Code-Then-Execute（先写代码再执行）
**做法**：让 LLM 生成一段**程序**，再由解释器执行；程序里**追踪数据来源**并在工具调用时执行策略。
**效果**：控制流被"固化"成代码，不可信数据无法改写控制流。
**代价**：需要可信的解释器和 provenance 追踪（**B1 的 CaMeL 走的就是这条路**）。

> 还有一个常见的是 **Context-Minimization（上下文最小化）**：只给 Agent 它需要的最小上下文，减少攻击面。

---

## 三、核心取舍（这段最该记住）

论文的立场：**这些模式都是拿"能力/可用性"换"安全"**。

| 模式 | 自主性 | 抗注入 |
|---|---|---|
| Action-Selector | 最低 | 最强（免疫） |
| Plan-Then-Execute | 低 | 强 |
| LLM Map-Reduce | 中 | 强（子任务隔离） |
| Dual LLM | 中 | 强 |
| Code-Then-Execute | 中 | 强 |

**选模式 = 在"Agent 要多自主"和"要多少安全保证"之间选一个点。**

---

## 四、★ 映射到你的卫星场景

**这五个模式可以直接当你的"连环锁"候选清单**，因为它们每一个都提供**一种不同角度的锁**：

| 模式 | 卫星场景怎么用 |
|---|---|
| **Action-Selector** | **遥操指令这种最高危动作**，可以让 Agent 只能"选择指令"，**执行结果不回流**——切断反馈链 |
| **Plan-Then-Execute** | 任务规划一次定死，**影像/遥测数据不能改规划**——直接防你导师说的"篡改认知"那一步 |
| **Dual LLM** | **最适合轻量化**：隔离 LLM 用星上小模型处理影像/遥测，特权 LLM 只在必要时调用（云端） |
| **Code-Then-Execute** | 把任务固化成可审计的程序，**provenance 追踪**能回答"这条指令的依据来自哪个数据" |
| **LLM Map-Reduce** | 多载荷/多区域任务并行，**一块被污染不影响其他块** |

**特别值得注意**：**Plan-Then-Execute 直接命中"篡改认知"这个威胁**——因为它的核心就是"让不可信数据无法改变动作序列"。如果你把"认知"定义成"当前计划"，那这个模式就是现成的防御。

**B2 缺什么**：它是**设计模式**，不是实验结果——**没有量化效果数字**，也没有多步攻击的评测。你的方案里要用它当"**设计依据**"，用 A1/A2 当"**实验依据**"。

---

## 五、局限

- 是**模式化建议**，不是实证结果（没有 benchmark 数字）
- 都需要**改造架构**，落地成本不低
- 论文自己也说：**没有哪个模式在所有场景都最优**，要按任务选
- 对"**只影响生成内容、不影响控制流/数据流**"的攻击同样无能为力（跟 CaMeL 同一个盲区）

---

## 六、一句话总结

**既然模型短期分不清指令和数据，就改架构：用"切断反馈""计划定死""特权/隔离分离""固化成代码"这些模式，让攻击即使骗过模型也改不了执行路径——代价是牺牲一部分自主性和可用性。**
