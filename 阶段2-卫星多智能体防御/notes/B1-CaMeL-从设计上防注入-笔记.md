# B1 笔记：CaMeL —— 从设计上防注入

> **论文**：Defeating Prompt Injections by Design（CaMeL）
> **作者**：Edoardo Debenedetti, Ilia Shumailov, Tianqi Fan, Jamie Hayes, Nicholas Carlini 等（**Google / Google DeepMind / ETH Zurich**）
> **出处**：arXiv:2503.18813 · 2025-06
> **本地 PDF**：`papers/B1 - CaMeL Defeating Prompt Injections by Design (2503.18813).pdf`（125 页，含大量附录）
> **代码**：<https://github.com/google-research/camel-prompt-injection>
> **一句话**：在 LLM 外面套一层**受保护的系统层**——把控制流和数据流**从可信的用户查询里显式抽出来**，让不可信数据**永远无法影响程序流程**；再用**能力（capability）**机制防止私有数据经未授权通道外泄。

---

## 一、核心思路（这段是整篇的骨头）

传统防御是"训练模型/写系统提示让它遵守策略"——CaMeL 认为这条路不可靠（系统提示本身就可被攻击）。

**CaMeL 换了个层次**：不指望模型分辨指令和数据，而是**在模型外面建一个系统层**，让模型根本没有机会把不可信数据当成指令。

两个机制：

### ① 控制流与数据流分离
从**可信的用户查询**里**显式提取**出：**控制流**（要做哪些步骤）和**数据流**（数据从哪来、到哪去）。

结果：**不可信数据检索回来之后，无法影响程序流程**——因为它只能填进"数据槽位"，改不了"要执行什么"。

### ② 能力（Capability）
用**能力**的概念，在**调用工具的时候**强制安全策略，防止私有数据经未授权的数据流外泄。

### ③ 实现：一个追踪溯源的自定义 Python 解释器
CaMeL 写了个自定义 Python 解释器，**追踪 provenance（来源）**并在工具调用时执行策略。

### ④ 理论上基于 Dual LLM 模式
来自 Willison (2023) 的 **Dual LLM pattern**：两个 LLM 分工——

- **Privileged LLM（特权 LLM）**：规划要做哪些动作，处理可信输入
- **Quarantined LLM（隔离 LLM）**：只负责处理不可信数据，**它说的话不能直接变成动作**

---

## 二、效果

在 **AgentDojo**（专门评测 Agent 安全的基准）上：

| | 任务解决率 |
|---|---|
| 无防御系统 | 84% |
| **CaMeL** | **77%（且带可证明的安全性）** |

**解读**：**牺牲 7 个点的可用性，换来"策略违规不可能发生"的保证**。论文原话是 "with some utility degradation, yet with guarantees that no policy violation can take place"。

---

## 三、明确的前提与不覆盖的范围（很重要，别误用）

论文自己列的假设：

1. **假设用户查询是可信的**
2. **假设用户不是从不可信来源粘贴过来的提示**
3. **如果系统有记忆，假设记忆没有被攻陷**

**明确不做的事**：

- **不防"文本到文本"的攻击**——如果攻击只改变生成内容、不影响控制流或数据流，CaMeL 不管

---

## 四、★ 映射到你的卫星场景

| CaMeL 的机制 | 卫星场景怎么用 |
|---|---|
| **控制流与数据流分离** | **这是"连环锁"最优雅的实现方式**：把"要做什么"（从可信任务定义来）和"用什么数据"（从不可信的遥测/影像来）彻底分开——影像数据再脏也改不了任务流程 |
| **能力（capability）** | 每个 Agent 拿到的是**被裁剪的能力**，而不是"什么都能干，但请自觉" |
| **Dual LLM（特权 + 隔离）** | **对卫星特别合适**：隔离 LLM 处理高熵的影像/遥测数据，特权 LLM 只做决策——**算力上也可以把隔离那个用小模型** |
| **可证明的安全性** | 你方案可以追求"**结构上不可能违规**"，而不只是"拦住了多少" |
| **代价：可用性降 7 个点** | 你要在方案里交代这个 trade-off——安全与可用性不可能同时最优 |

**关键启发**：CaMeL 的**前提假设**正好是你场景的**风险点**——
- "假设用户查询可信" → 卫星上，**上行指令可信吗？**
- "假设记忆没被攻陷" → 卫星上，**长期记忆/历史状态在星上，会被攻陷吗？**
- "不防文本到文本攻击" → 你导师要防的**第二步"篡改认知"**，恰好是"影响认知但不一定影响控制流"——**这是 CaMeL 的盲区，也是你的位置**

---

## 五、局限

1. **需要可信的用户查询**——如果攻击者能改用户查询，整个设计前提就没了
2. **不管文本到文本的攻击**
3. **可用性下降**（84% → 77%）
4. **工程复杂**：自定义解释器、provenance 追踪，移植成本不低

---

## 六、一句话总结

**别指望模型自己分辨"指令"和"数据"——在外面套一层系统，把控制流从可信查询里抽出来，让不可信数据只能填数据槽位、改不了程序流程；再用能力机制限制工具调用，就能做到"结构上不可能违规"，代价是掉 7 个点可用性。**
