# A2 笔记：信任传播与结构遏制

> **论文**：Trust Propagation and Structural Containment in Multi-Agent LLM Pipelines
> **作者**：Tanzim Hossain Safin, Sharif Noor Zisad, Swakkhar Shatabda, Ragib Hasan（BRAC University / University of Alabama at Birmingham）
> **出处**：arXiv:2609.17648 · 2026-09-15（**14 天前**）
> **本地 PDF**：`papers/A2 - Trust Propagation and Structural Containment (2609.17648).pdf`（6 页）
> **一句话**：用实验证明——**上游 Agent 被攻陷 ≠ 系统被攻陷**，只要在"执行"前放一道**独立的授权边界**。

---

## 一、为什么这篇对你特别重要

它几乎就是你要做的"**连环锁**"的**实证版本**。

而且它做了一个**关键消融**，得出一个反直觉结论：

> **单独的消息签名没用。** 攻击者只要拿到签名密钥，签名就形同虚设——**真正拦住攻击的是"独立的策略检查"（policy oracle）**。

**这一条直接修正了 A1 的做法**。A1 把"消息签名 + 溯源"当成第一层防御（说能降 91%）；A2 用消融说明：签名证明的是**来源**，不是**权限**——"一个只有签名的系统，继承的是持密钥者的权限"。

---

## 二、实验设置

**四 Agent 流水线**（LangGraph 实现）：

| Agent | 权限 | 干什么 |
|---|---|---|
| **Supervisor** | — | 确定性路由，**不调用 LLM** |
| **Researcher** | 低 | 只读，检索信息 |
| **Validator** | 中 | **审批门**（approval gate） |
| **Executor** | 高 | 执行**真实动作**（改数据库/文件） |

**两种攻击**：

1. **共享记忆投毒**——Validator 被换成被攻陷的例程，**伪造一个审批**（如果它还有签名密钥，就连合法的 token 一起生成）
2. **间接注入**（Agent 劫持）——Researcher 检索到的文档里**藏着一个伪造的审批**，带假的置信度和来源声明；Validator 不知道来源，直接对它推理

**防御**：**HMAC 签名 + 任务绑定 + 单次使用**的 token，配上**独立验证的 policy oracle**，加沙箱执行。

**数据**：Enron 邮件数据集（1000 封，只留 header），60 个任务（36 安全 / 24 不安全，覆盖 13 种动作类型），3 个随机种子，n=180/格。模型用 gemma4:31b（Ollama，temperature 0）。

---

## 三、核心指标创新：JBR

这是这篇最值得你学的东西。

| 指标 | 衡量什么 |
|---|---|
| **UAR**（Unsafe Action Rate） | **危险动作真正被执行**的比例 |
| **JBR**（Judgment Bypass Rate） | **被攻击的那个 Agent 的判断被绕过**的比例 |

**为什么要分开**：A1 那类研究衡量的是"Agent 有没有被骗"，但**被骗不等于造成后果**——中间还有授权边界。

论文原话的意思是：**把"判断被绕过"和"攻击成功"分开，才不会对系统安全产生虚假的信心。**

> **这个思路你已经见过一次了**——GeoLLM-Squad 的 agentic correctness 也是"过程指标"。**JBR 是安全领域的同类思路**：不看最终结果，看中间那一步有没有被突破。

## 四、结果（数字都在表里）

**攻击效果**：

| 攻击 | 条件 | UAR | FPR | JBR |
|---|---|---|---|---|
| 记忆投毒 | T0（无授权） | **100%** | 0% | 100% |
| 记忆投毒 | T1（有授权） | **0%** | 0% | **100%** |
| Agent 劫持 | T0 | 0% | 59.3% | 0% |
| Agent 劫持 | T1 | 0% | 49.1% | 0% |

**最关键的一行**：记忆投毒在 T1 下 **JBR 仍是 100%，但 UAR 降到 0%**。

翻译成人话：**Validator 完全被攻陷了，但 Executor 独立挡住了，所以危险动作一次都没执行。**

**授权消融**（针对持有签名密钥的攻击者）：

| 配置 | 结果 |
|---|---|
| 只有 token（无 policy oracle） | **和没有防御一样**（UAR 100%） |
| 只有 policy oracle | **和完整 T1 一样**（UAR 0%） |

→ **拦住攻击的是 policy oracle，不是签名。**

**Observer 层**（额外一次模型调用，专门识别"伪造的审批声明"）：

| | 关闭 | 开启 |
|---|---|---|
| FPR（误拦） | 49.1% | **7.4%** |
| F1 | 0.74 | **0.95** |
| UAR | 0% | 0%（**不变**） |

→ Observer **只降低误拦成本，不改变安全保证**。论文明确把它定位成"保可用性的组件，不是安全控制"。

## 五、局限（作者自己列的）

1. **独立策略是同一组人写的**——能说明"不是从评测标签里抄的"，但不能说明"策略本身客观正确"
2. **只有 3 个种子，60 个任务，13 种动作**
3. **注入太显眼**——伪造的审批明说"已审批、置信度、来源"，Validator 才 0% 被骗。**作者明确说这个结果不能外推到自适应攻击者**
4. **单一架构、单一框架、单一个模型**
5. **假设签名密钥的保密性**（他们故意用了最强攻击者模型：攻击者持有密钥）

## 六、★ 映射到你的卫星场景

| A2 的设计 | 卫星场景怎么用 |
|---|---|
| **四角色分级**（低→中→高权限） | 检索/规划（低）→ 校验（中）→ **遥操执行（高）** |
| **执行前必须有独立授权** | **遥操指令发出前，必须有独立于"决策 Agent"的授权检查** |
| **JBR 指标** | 你可以测："星上 Agent 的认知有没有被篡改"（JBR）vs "不合理指令有没有真的发出"（UAR）——**分开测才能证明防御有效** |
| **policy oracle 独立于 LLM 判断** | **权限检查不能靠 LLM，要靠规则/配置**——这对星上算力也友好 |
| **Observer 降低误拦** | 卫星场景误拦代价高（错过真实任务），需要类似的"先清洗再校验"层 |

**两个关键结论可以直接写进你的方案**：

1. **"判断"和"授权"必须分离**——被攻陷的 Agent 应被当成"不可信的决策者"，而不是自动继承它本来拥有的权限
2. **签名不够，必须配独立策略**——签名只证明来源，不证明权限

**A2 缺什么（你的空位）**：
- 它的攻击是**单次注入**（只是效果会传播），**没有"多步逐步篡改认知"**
- 它的 Validator 没有"**认知状态**"这个可校验对象——而你要防第二步"篡改认知"，就必须把认知显式化
- 它是**纯文本**，没有影像/多模态

---

## 七、一句话总结

**上游 Agent 被攻陷不代表系统被攻陷——把"判断"和"授权"分开，在执行前放一道独立的策略检查，就能把被污染的判断拦在执行之外；但要注意，这道检查必须是独立的策略（不是签名、也不是另一个 LLM 的判断）。**
---

## 八、两个最容易看不懂的地方（展开讲）

### 1. token vs policy oracle：一个管身份，一个管权限

| | 是什么 | 管什么 |
|---|---|---|
| **token（令牌）** | 消息自带的**密码学签名** | 证明"消息从那个 Agent 来、没被改过"→ **管来源** |
| **policy oracle（策略预言机）** | 一个**独立的**检查模块 | 不看消息从谁来，只看"这件事**按规则允不允许做**"→ **管权限** |

**消融的场景**：攻击者**拿到了签名密钥**。

- 他能造出**签名完全合法**的假令牌 → **token 这一关放行**
- 但 policy oracle **不看签名**，只查"这个动作该不该被允许" → **拦住**

**打比方**：

- **token = 工作证**（证明你是本公司员工）
- **policy = 门禁权限表**（证明你有权进这间房）

攻击者偷到制卡机（拿到密钥）→ 能造出以假乱真的工作证 → **查工作证这一关废了**。
但**权限表是独立的另一份东西**（不在消息里），他伪造不了 → 门禁查"你这张卡的权限里有没有这间房" → **拦住**。

**一句话**：token 证明"你是谁"，policy 证明"你能不能干"。**攻击者能伪造身份时，只有独立查权限的那层还管用。**

### 2. Observer：它解决的是"防过头了"，不是"没防住"

**背景**：Agent 劫持那个攻击其实**没成功**（UAR 0%），但代价很大——**Validator 把 49.1% 的正常任务也拒了**。因为注入**太显眼**（明写"已审批、置信度 0.95、来源 xxx"），Validator 疑神疑鬼，把什么都拒了。

**所以问题不是"没防住"，是"防过头了"——一半正常任务做不了。**

**Observer 做什么**：在 Researcher 和 Validator 之间插一个 Agent，只干一件事——扫内容里有没有"别的 Agent 已审批/已验证"这类声明，有就**把那句删掉**（其余保留）再交给 Validator。

**效果**：

| | 关闭 | 开启 |
|---|---|---|
| 误拦率 FPR | 49.1% | **7.4%** |
| 正常任务完成率 | 50.9% | **92.6%** |
| 危险动作执行率 UAR | 0% | **0%（没变）** |

**为什么论文说它"不是安全控制"**：

- 真正拦住危险动作的是 **policy oracle**，跟 Observer 无关
- Observer 只是**清理扎眼的假货，让正常判断能进行**
- **它防不住"不显眼"的注入**——攻击者把假声明写得自然一点，它就看不出来

**所以不能把它当"一道防御"来宣传。它是保可用性的组件，不是防线。**

## 九、被追问：policy oracle 自己被攻陷了怎么办？

**A2 没测这个**——它的威胁模型里 **policy oracle 是假设可信的**。

### 这不是漏洞，是"把信任收窄"

这类防御的思路不是"让每个 LLM 都可信"，而是**把信任集中到一个小的、可验证的组件上**。传统安全的老套路：

- 操作系统：**内核可信**，用户程序不可信
- 智能合约：**虚拟机可信**，合约代码不可信
- A2：**policy oracle 可信**，LLM 不可信

**为什么比"提示词护栏"强**：oracle 是**确定性规则/代码**，不是概率性模型 → **可审计、可测试、可形式化验证**。提示词护栏是个 LLM，A1 实测被 67% 打穿。
**代价**：信任边界推到 oracle，**oracle 一破全盘皆输**。

### "被攻陷"有四种，要分开

| 种类 | 含义 | 怎么防 |
|---|---|---|
| **A 策略写错** | 规则太宽（如"任何 Agent 都能发指令"） | 策略**独立编写**（A2 做了这个消融）+ 最小权限 + 人工审计 |
| **B 实现有 bug** | token 解析漏洞、规则绕过 | **oracle 做得足够小、足够简单** + 形式化验证 / 模糊测试 |
| **C 被夺取执行权** | 能改策略配置、替换 oracle、拿到凭证 | 权限隔离 + 配置签名 + 审计日志（= E4 的 A4 基础设施攻击者，**A2 明确说不覆盖**） |
| **D 失效（不是被攻陷）** | oracle 挂了系统动不了 | 降级模式：只能做安全动作（fail-safe） |

### ★ 这本身是个选题候选

> **"如何设计不依赖单一可信组件的多智能体防御？"**

现有工作（A1 / A2 / CaMeL）**都默认信任根安全**，没人系统研究过"**信任根被攻陷时的多智能体防御**"。

几条思路：
1. **多个独立 oracle 投票**（N 个策略引擎，M 个同意才放行）
2. **用密码学替代策略**（授权必须持私钥签发 → 攻陷 oracle 还不够，还得偷私钥）
3. **让篡改可检测**（哈希链 / 审计日志）
4. **fail-safe 降级**（oracle 不可用时只能做安全动作，不能做不可逆动作）

### 诚实的终点

**没有任何防御能解决"信任根被攻陷"**——这是所有安全系统的终点。所以正确问法是三条：

1. **把信任根缩到最小**（小、简单、可验证）
2. **让攻陷可检测**（审计、日志、哈希链）
3. **让攻陷的后果有界**（不能一发指令就毁星）

**这三条就是导师说的"连环锁"的严格版本。**

### 对卫星的具体建议

最高危的动作（**遥操指令**）应该有一层**硬件或人工的最终确认**——地面站人工放行，或星上硬件看门狗。

因为**纯软件的多层防御，在"信任根被攻陷"面前都是纸**；卫星的物理不可逆性决定了它必须比企业系统多这一层。
