# B2 笔记：六个安全设计模式（附 10 个案例）

> **论文**：Design Patterns for Securing LLM Agents against Prompt Injections
> **作者**：Luca Beurer-Kellner（Invariant Labs）、Beat Buesser（IBM）、Edoardo Debenedetti（ETH）、Florian Tramèr（ETH）、Andrew Paverd（Microsoft）等 **14 人**（作者按字母序；**Google / IBM / Microsoft / ETH / EPFL / Swisscom / AppliedAI 等联合**）
> **出处**：arXiv:2506.08837 · 2025-06（32 页）
> **本地 PDF**：`papers/B2 - Design Patterns for Securing LLM Agents (2506.08837).pdf`
> **一句话**：给出**六个**有**可证明抗注入性**的 Agent 设计模式，逐个分析安全性与可用性的取舍，并用**10 个案例**说明怎么落地。

---

## 一、它的核心主张（先记住这个转向）

论文先承认一件事：

> 我们**不相信通用 Agent 能提供有意义且可靠的安全保证**。

然后把问题换掉——**这是全篇最关键的一步**：

> 与其问"怎么让通用 Agent 安全"，不如问：**今天能造出哪些"既能干活、又抗注入"的 Agent？**

**所以这套模式的性质是**：

> 它们**故意给 Agent 加约束**，**明确限制它做任意任务的能力**。
> 论文自己说，这是在 **Agent 可用性**和**安全性**之间取一个**有价值的折中**。

**注意**：这不是"让模型变强"，是"**把 Agent 的能力范围缩小到能保证安全的那部分**"。

---

## 二、共同原则（一句话，所有模式都从这来）

> **一旦 LLM Agent 吞下了不可信输入，就必须约束它，使得那份输入"不可能"触发任何有后果的动作。**

"有后果的动作" = 对系统或环境有负面影响的动作。**最低限度**：受限 Agent **不能调用会破坏系统完整性或机密性的工具**。

**另外，输出本身也不能有下游风险**：
- 泄露敏感信息（比如通过内嵌链接）
- 操纵后续 Agent 行为（比如对用户查询生成有害回答）

### ★ 论文明确区分了两类东西

| 类别 | 是什么 | 论文的态度 |
|---|---|---|
| **设计模式（本节 6 个）** | 约束 Agent 能力的**架构做法** | 按任务选，**没有哪个模式在所有场景最优** |
| **最佳实践（附录 A）** | 沙箱运行、敏感操作请用户确认等 | **每个 Agent 都应该尽量都做** |

**这个区分别搞混**：模式是"选一个"，最佳实践是"都要有"。

## 三、六个模式（逐个）

### ① Action-Selector（动作选择器）—— 最严格

**做什么**：**切断工具输出回流给 Agent 的通道**。Agent 只当一个"动作选择器"，把进来的自然语言请求**翻译成一到多个预定义的工具调用**。

**类比**：一个**由 LLM 调制的 `switch` 语句**——从一份动作清单里选。

**动作可以模板化**：比如一条**预定义的 SQL 查询，只留占位符让 Agent 填**。

**例子**（客服 chatbot 的固定动作集）：
- 取用户最近一笔订单的链接
- 引导用户去设置页改密码
- 引导用户去设置页改支付信息

**安全理由**：**动作结果不回到 Agent** → 注入**没有可以影响后续的通道** → 论文说它**对提示注入免疫**。

**它也能防"用户输入里的注入"**：做法是**在 Agent 回复用户之前，把 prompt 从上下文里移除**（见模式 ⑥）。

**代价**：**几乎放弃了自主性**——没有反馈就没有多步推理。

---

### ② Plan-Then-Execute（先规划后执行）

**做什么**：**允许工具输出回流**，但**不许输出影响"选哪些动作"**。Agent 先定死一个动作计划（固定的一串动作），然后照着执行。

**论文的定位**：这是一种**"控制流完整性（control flow integrity）"**保护。

**例子**（有邮件和日历读写权限的助手）：

```
用户："把今天的日程发给我老板 John Doe"

定死的计划：
  1. calendar.read(today)
  2. email.write(<日程>, "john.doe@company.com")

日历数据里的注入：
  ✗ 不能注入新指令（改不了动作序列）
  ✓ 可以任意改那封邮件的内容
```

**★ 论文自己承认的漏洞**（原话）：日历里的注入"**could, however, arbitrarily alter the body of the email**"。

**这就是 CaMeL 要补的那个数据流漏洞**（见 B1 笔记）——**控制流守住了，数据流没守住**。

**不防什么**：**不防用户提示里的注入**。

**代价**：计划定死，临机应变的任务不好用。

---

### ③ LLM Map-Reduce（LLM 分治）

**要解决**：Plan-Then-Execute **还是允许"工具输出影响工具调用的参数"**。

**做什么**：主 Agent **派发隔离的"子 Agent"**去处理**单块**第三方数据（**map** 操作）。

因为**每个子 Agent 都可能被单独注入**，所以必须强制它**不能做任何有害操作**（比如调任意工具）。

**然后 reduce**，两种设计：

| 设计 | 做法 |
|---|---|
| **(1) 不用 LLM** | reduce 只用**对单块输入被篡改鲁棒**的操作（类似 Xiang et al. 2024） |
| **(2) 用 LLM** | 但**对 map 的输出加强约束**——比如用一个**正则要求 map 的输出必须是数字** |

**例子**（找含发票的文件并发给财务）：

- **朴素实现**：某个文件里注入指令，让 Agent 去读任意文件并把内容发给攻击者 ← **危险**
- **Map-Reduce 实现**：**每个文件派一个 LLM**，只返回一个**布尔值**（这个文件是不是发票）→ 再聚合出所有匹配文件，用另一个 LLM 写并发送邮件

**为什么安全**：**恶意文件最多只能骗 map 那个 LLM 说"我是发票"**——而这个效果**跟直接把文件换成一份真发票是一样的**，无害。

**核心保证**：**一个恶意文档无法影响对另一个文档的处理。**

---

### ④ Dual LLM（双 LLM）

**关系**：**LLM Map-Reduce 是它的一种特例**（论文原话）。这是 Willison (2023b) 提出的更一般的模式。

**两个 LLM**：
1. **Privileged LLM（特权）**：接收指令、规划动作、**能用工具**
2. **Quarantined LLM（隔离）**：被特权 LLM 在需要处理不可信数据时调用，**不能使用任何工具**，只能处理文本

**★ 关键设计：怎么切断反馈回路**——两种做法：

| 做法 | 内容 |
|---|---|
| **简版** | 隔离 LLM 的输出必须满足**安全约束**（同上面的 map 约束） |
| **进阶版（很漂亮）** | 隔离 LLM 返回**符号响应**，特权 LLM **能操作但看不到内容**；符号由**第三个组件**——一个**传统软件（非 LLM）的 orchestrator**——在**函数调用时**替换成实际值 |

**符号响应怎么工作**（论文例子）：

```
特权 LLM：让隔离 LLM 在一段不可信文本里找一个邮箱地址，存进 $VAR

特权 LLM 可以：
  ✓ 符号式地操作这个变量（比如再调一个隔离 LLM 处理它的内容）
  ✓ 把 $VAR 当参数传给「发邮件」函数
  ✗ 不能解引用（dereference）它的值 ← 一旦解引用就引入注入了

实际值由 orchestrator 在函数调用的那一刻替换进去。
```

**这个设计的思想**：**让特权 LLM 操作"引用"而不是"值"**——它永远不知道那个值是什么。

---

### ⑤ Code-Then-Execute（先写代码再执行）

**关系**：**把 Dual LLM 推到极限**，也**是 Plan-Then-Execute 的推广**——把"规划"换成"**显式的程序**"。

**做什么**：Agent **写一段正式的程序**来完成任务。程序里可以：

- 调用 Agent 可用的工具
- **生成无特权的 LLM** 去处理不可信文本

**这个模式的具体实例就是 B1 的 CaMeL**（论文引的 Debenedetti et al. 2025）。

**例子**（还是"把今天的日程发给老板"）：

```python
x = calendar.read(today);
x = LLM("format this data", x);
email.write(x, "john.doe@company.com");
```

**论文明确承认的漏洞**（和 Plan-Then-Execute 一样）：

> **同样地，我们无法阻止日历数据里的注入改变发给 John 的邮件内容。**

**代价**：需要可信的解释器 + provenance 追踪（**CaMeL 走的就是这条**）。

---

### ⑥ Context-Minimization（上下文最小化）—— 正交的一条

**要解决**：上面的模式**都还允许"用户提示里的注入"**——要么用户本身是恶意的，要么**用户不小心从攻击者网站复制粘贴了恶意内容**。

**做什么**：**在多次交互中，把不必要的内容从上下文里移除。**

**例子**（客服 chatbot 被注入要折扣）：

```
恶意用户：问一台新车的报价，同时注入指令要一个大折扣

系统做法：
  1. 先让 Agent 把用户的请求翻译成一条数据库查询（查最新报价）
  2. 在把结果返回给客户之前，把【用户的 prompt】从上下文里移除
  → 注入无法再影响 Agent 的回复
```

**关键**：**用户提示用来决定"做什么"（比如调哪个工具），但之后就从上下文里删掉**，防止它再影响回复。

**这条是正交的**：其它五个管**工具输出**这条线，它管**用户提示**这条线。

## 四、★ 六个模式的关系（这张图最有用）

```
【控制流这条线】  灵活度递增
  Action-Selector  →  Plan-Then-Execute  →  Code-Then-Execute
  （无反馈回流）      （计划定死）           （写成程序）
                                          └─ CaMeL 就是这个的具体实现

【数据隔离这条线】
  LLM Map-Reduce   →  Dual LLM
  （子 agent 隔离）   （Map-Reduce 的推广：特权 + 隔离）

【正交的一条】
  Context-Minimization   ← 管"用户提示"，不管"工具输出"
```

**哪个防什么、保留多少自主性**：

| 模式 | 防工具输出的注入 | 防用户提示的注入 | 自主性 |
|---|---|---|---|
| **Action-Selector** | ✅ 最强（免疫） | ✅（配合 ⑥） | **最低** |
| **Plan-Then-Execute** | ⚠️ 部分（**参数仍可被改**） | ❌ | 低 |
| **LLM Map-Reduce** | ✅ 子任务互相隔离 | ❌ | 中 |
| **Dual LLM** | ✅ 隔离 LLM 无工具 | ❌ | 中 |
| **Code-Then-Execute** | ⚠️ 部分（**同 Plan-Then-Execute**） | ❌ | 中 |
| **Context-Minimization** | ❌ | ✅ | — |

**★ 最需要注意的一行**：**Plan-Then-Execute 和 Code-Then-Execute 都只防"改动作"，不防"改参数"**。

**这正是 CaMeL 的出发点**——B2 是**设计空间地图**，CaMeL 是**地图上某条路的具体施工**。

## 五、用"结构约束 vs 策略检查"重新看这套模式

| 模式 | 属于哪类 |
|---|---|
| Action-Selector | **结构约束**（切断通道，不是"判断该不该给"） |
| Plan-Then-Execute | **结构约束**（计划先定死） |
| LLM Map-Reduce | **结构约束**（子任务物理隔离）+ 少量策略（map 输出约束如正则） |
| Dual LLM | **结构约束**（隔离 LLM 没有工具） |
| Code-Then-Execute | **结构约束 + 策略**（CaMeL 的 capability 是策略检查） |
| Context-Minimization | **结构约束**（把 prompt 从上下文删掉） |

**→ B2 这六个模式，绝大部分是"结构约束"**（详见 `框架-结构约束vs策略检查.md`）。

**这就是它们比"内容过滤"强的原因**：**不依赖策略完备，而是让攻击没有通道。**

**代价也很清楚**：**每一个都在牺牲能力**——论文自己说"这些模式**故意限制** Agent 做任意任务的能力"。

## 六、10 个案例研究（论文第 4 节）

每个案例都是同一个结构：**应用背景 → 功能需求 → 安全假设 → 朴素实现（有漏洞）→ 稳健设计（用哪些模式）**。

1. **OS 助手**（带模糊搜索）
2. **SQL Agent**
3. **邮件与日历助手**
4. **客服 chatbot**
5. **预订助手**
6. **产品推荐**
7. **简历筛选助手**
8. **药品说明书 chatbot**

**为什么案例研究本身有价值**：它示范了"**同一个应用，怎么从朴素实现改成安全实现**"——**这正好是写方案时"防御设计"一节的写法模板**。

## 七、★ 映射到你的卫星场景

| 模式 | 卫星场景怎么用 |
|---|---|
| **Action-Selector** | **遥操指令**：Agent 只能从**预定义指令模板**里选（带占位符），**执行结果不回流**——最高危动作适合用这条 |
| **Plan-Then-Execute** | 任务规划**一次定死**，影像/遥测数据**不能改规划** ← **直接命中"篡改认知"** |
| **LLM Map-Reduce** | 多区域/多载荷任务并行，**一块数据被污染不影响其他块** |
| **Dual LLM** | **最省算力**：隔离 LLM 用**星上小模型**处理影像/遥测，特权 LLM 只在必要时调用 |
| **Code-Then-Execute** | 任务固化成**可审计的程序**；配 capability 追踪数据来源 |
| **Context-Minimization** | **地面指令用完即删**——防止它残留下来影响后续回复 |

**★ 特别注意 Plan-Then-Execute 的定位**：

**它直接命中"篡改认知"这个威胁**——因为它的核心就是"**让不可信数据无法改变动作序列**"。

**如果你把"认知"定义成"当前计划"**，那这个模式就是现成的防御。**但**：它防不住"改参数"（论文自己承认），所以**还得配 capability**（= CaMeL 的组合）。

**→ 你的"连环锁"很可能是这个组合**：
**Plan-Then-Execute（结构约束，定死动作）+ capability 检查（策略检查，卡住参数）+ 认知状态显式化（独立校验漂移）**

## 八、局限

1. **是设计模式建议，不是实证结果**——**没有 benchmark 数字**（跟 A1/A2 不同）
2. **都需要改造架构**，落地成本不低
3. **没有哪个模式在所有场景最优**——要按任务选
4. **共同的盲区**：对"**只影响生成内容、不影响控制流/数据流**"的攻击无能为力（跟 CaMeL 的 non-goal 一样）→ **而这正是"篡改认知"可能落的位置**

**怎么用它**：**当"设计依据"，不当"实验依据"**。
- **设计依据**：B2（模式）+ 你的认知状态框架
- **实验依据**：A1（威胁模型与量化）+ A2（消融与指标）

---

## 九、一句话总结

**既然通用 Agent 保证不了安全，就把问题换成"哪种 Agent 既有用又抗注入"——六个模式都是在"不可信输入"和"有后果的动作"之间**切断通道**：不让结果回流、把计划定死、把子任务隔离、让隔离 LLM 没有工具、把规划变成程序、把用户提示用完即删。它们绝大多数是结构约束（不靠策略完备），代价是牺牲 Agent 的能力范围。**
