## 一、威胁（3 页）

### P1 · 封面
- 标题：**卫星多智能体安全：多步注入攻击与防御**
- 副标题：**领域调研：威胁、防御路线与现状**
- 精读 7 篇 + 相关 5 篇

### P2 · 多步注入攻击链
```
① 获取卫星运行参数 → ② 篡改认知范围，使其合理化 → ③ 执行不合理操作 / 篡改遥操数据
```
**必须界定清楚**：「篡改认知」指攻击者**不改 Agent 的代码和系统提示**，而是**污染它读到的输入数据**，让 Agent 自己形成错误判断。
→ 认知是内部信念，**不是被直接改写，是被污染输入诱导漂移**。

### P3 · 场景边界与卫星场景的特殊性
- **场景边界**：星上 MAS（Agent 全在星上）vs 天地一体化 MAS（跨链路，信任边界在链路上）
- **三条特殊性**：数据多模态 / 动作物理不可逆 / 算力受限

## 三、领域地图（8 页）

### P5 · 领域框架：A-I-R（出处 E4 SoK，197 篇）
- **A 攻击者位置 → I 交互接口 → R 系统级风险**
- 核心论点：单独安全的 Agent，一起用会失败
- 六个接口 / 四个位置（**A3 成员级是多智能体独有的**）
- 收尾：卫星场景里最贴合这个威胁的是**成员级攻击者**

### P6 · 攻击侧①：多步攻击怎么工作（Crescendo）
- 每一步引用模型自己上一轮的回答，逐步升级
- 比当时最好越狱强 **29%–61%**；**每轮单看都无害** → 单轮过滤必然失效
- **区分**：Crescendo 是**单智能体自迭代**的多步越狱，不涉及 Agent 间状态传递

### P7 · 攻击侧②：一次攻击的完整形态（A1 的例子）
- 合规 Agent 收到工具返回里的注入 → 污染批准上浮 → 编排者不复核直接下发
- **四类成功率**：直接注入 19% ｜ **工具输出间接注入 43%** ｜ **Agent 间消息 31%** ｜ 级联 28%
- 标注：**通用基准上的数字，非卫星场景**

### P8 · 防御侧路线①：架构分层（A1）
四层防御 + 效果表；总体 **31.2% → 4.2%**，延迟只多 **4.7%**，净化器误判率 **2.3%**

### P9 · 防御侧路线②：独立授权（A2）
- 记忆投毒：无授权 UAR 100% → 有授权 **UAR 0%，但 JBR 仍 100%**
- **关键消融**：只有签名 = 没防御；只有独立策略 = 完整防御
- 结论：**签名证明来源，不证明权限**

### P10 · 防御侧路线③：从设计上防（CaMeL + B2）
- CaMeL：Dual LLM 不够（控制流守住，数据流还能被操纵，类比 SQL 注入）→ 编译成代码 + capability + 每次调工具前查策略；AgentDojo **67%**（arXiv v2 是 77%）
- B2：六个架构模式，共同点是**切断通道**不是检查内容；区分"设计模式"与"最佳实践"

### P11 · 防御侧路线④：推测—验证与有状态防御 ★ 本次新补
| 工作 | 做法 | 效果 |
|---|---|---|
| Speculative Safety Honeypot（ICML 2026） | 小模型多智能体做推测—验证，建轨迹树 | 提前发现多轮意图 |
| VIGIL（ACL 2026） | 工具流「先验证再提交」 | ASR 再降 22%+，可用性翻倍 |
| CoopGuard（TIFS 投稿） | 多智能体协作：干扰 / 误导 / 取证 | ASR 平均降 69%，攻击方 token +199% |
| Adaptive Adversaries（基准） | 自适应跨轮攻击基准，945 场对抗 | **第一轮 0–1%，15 轮 7.9–16.8%** |

**共同点**：都不再靠"拦住单次输入"，而是维护跨轮状态、预测未来。

### P12 · 防御的分类：结构约束 vs 策略检查
| | 结构约束 | 策略检查 |
|---|---|---|
| 怎么工作 | 架构层面限制攻击路径 | 运行时判断后放行 / 拒绝 |
| 现有工作的例子 | Action-Selector、Plan-Then-Execute、按角色裁权限 | policy oracle、capability、内容过滤 |
| 押在哪 | 不依赖运行时判断 | 策略完备 + 组件可信 |

**两类的强弱不同**——这是读这些论文时最能区分它们强弱的维度。

## 四、领域现状（5 页，重点，慢讲）

### P13 · 现有防御都在动作层
| 防御 | 观测什么 | 不管什么 |
|---|---|---|
| CaMeL 的 capability | 数据来源与访问权限 | 不校验数据本身真假 |
| Security policy | 动作允不允许 | 做这个动作的理由 |
| Plan-Then-Execute | 动作序列 | 计划背后的判断依据 |
| Policy oracle（A2） | 权限表 | 认知有没有漂移 |

### P14 · 相关工作的边界：动作 vs 信念
**先说更正**：不能说"认知层没人做"——ICML 2026 的 SSH 已经很近了。

| 现有工作 | 观测什么 | 不看什么 |
|---|---|---|
| Speculative Safety Honeypot | 未来动作、轨迹树演化 | 它相信什么 |
| VIGIL | 工具流的意图 | 同上 |
| CoopGuard | 交互日志里的攻击模式 | 同上 |
| CaMeL / policy oracle | 数据流与动作权限 | 同上 |

**落点**：它们都在动作空间判断，**而一个攻击可以完全不改动作**。

### P15 · 一个具体场景：不改动作，只改认知
```
气象报告注入 → Agent 相信 → 写进给操作员的报告
  · 没调工具 → 控制流正常
  · 无数据外泄 → 数据流正常
  · 只是「认知错了」→ 现有防御看不见
↓
操作员照报告下指令 → 人变成攻击的执行端
```
**系统边界备注**：本案例展示人机闭环下的认知污染；若把地面决策 Agent 纳入边界，则属天地一体化 MAS。

### P16 · 为什么现有机制够不着：来源 ≠ 真伪
| | 问的是什么 | 能不能自动验证 |
|---|---|---|
| provenance（来源） | 这个值从哪来 | 能——签名、链路记录 |
| validity（真伪） | 这个值是不是真的 | 不能——需要跟事实对照 |

**三条路走不通**：过滤 / 只改数据不写指令 / 查上游。
**边界**：卫星场景"事实真值"本身就很难获取。

### P17 · 领域现状小结
**共识三条**：单步防护不够 ｜ 提示级不可靠，要架构级 ｜ 评测必须多轮 + 自适应
**未解决三条**：有状态防御的开销 ｜ 来源可验证但真伪不能 ｜ "不改动作只改认知"怎么观测
**结构性事实**：四条技术路线**都假设算力充裕**
